# Техническая документация: Система учёта посещаемости

## Краткая архитектура
Система построена по клиент-серверной модели:
- **Клиент** (веб/мобильное приложение) — интерфейс для преподавателей и студентов.
- **API-сервер** — REST-сервис, реализующий бизнес-логику учёта посещаемости.
- **База данных** — реляционное хранилище (PostgreSQL) для персистентности данных.

В рамках учебной задачи акцент сделан на документации и описании API. Реализация API может быть выполнена в виде mock-сервера или статической OpenAPI-спецификации, отображаемой через Swagger UI / Redoc.

## Ключевые сущности предметной области

### Занятие (Class)
- `id` (UUID) — уникальный идентификатор занятия
- `subject` (string) — название предмета
- `teacher_id` (UUID) — идентификатор преподавателя
- `group_id` (UUID) — идентификатор группы
- `date` (ISO 8601) — дата и время занятия
- `duration_minutes` (integer) — длительность в минутах

### Студент (Student)
- `id` (UUID) — уникальный идентификатор
- `full_name` (string) — ФИО
- `group_id` (UUID) — идентификатор группы

### Отметка о присутствии (Attendance)
- `id` (UUID)
- `student_id` (UUID)
- `class_id` (UUID)
- `status` (enum: `present`, `absent`, `late`)
- `marked_at` (ISO 8601) — когда была проставлена отметка

## Бизнес-логика
- **Процент посещаемости студента** = `(количество отметок "present" + "late") / общее количество занятий группы × 100%`.
- **Порог посещаемости** — настраиваемый параметр (по умолчанию 70%). Студенты, у которых процент ниже порога, попадают в отчёт для куратора/деканата.
- **Одна отметка на студента на занятие** — повторная отметка перезаписывает предыдущую.
- **Нельзя отметить присутствие на будущее занятие** — валидация по полю `date`.

## Как запустить и посмотреть документацию
Поскольку задача сфокусирована на документации, минимальный сценарий просмотра API:

1. Открыть [Swagger Editor](https://editor.swagger.io/)
2. Скопировать содержимое файла `openapi.yaml` в левую панель
3. В правой панели отобразится интерактивная документация с примерами запросов и ответов

Альтернативно — [Redoc](https://redocly.github.io/redoc/) или локальный Swagger UI через `npx @redocly/cli preview-docs openapi.yaml`.

| `DEFAULT_THRESHOLD` | Порог посещаемости по умолчанию, % | `70` |
| `LOG_LEVEL` | Уровень логирования | `info` |

## Соглашения по API
- Формат данных: JSON
- Аутентификация: Bearer-токен (заголовок `Authorization`)
- Коды ответов: `200` — успех, `201` — создано, `400` — ошибка валидации, `404` — не найдено, `500` — внутренняя ошибка
- Даты — в формате ISO 8601 (`2026-11-27T10:00:00Z`)
- Идентификаторы — UUID v4
- Пагинация: параметры `limit` и `offset` для списковых операций

## Ограничения и допущения
- В учебной реализации данные хранятся в памяти или в файле; для продакшена требуется полноценная БД с миграциями.
- Не реализована аутентификация и ролевая модель (в спеке описана как заглушка).
- Не предусмотрена синхронизация с внешними системами (деканат, LMS).
